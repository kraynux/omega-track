**Omega-track** — инструмент TUI + CLI, который по IP, IPv6-адресу или домену строит максимально полную цифровую идентичность: кто отвечает за этой целью, каким путём до неё доходит трафик и с каким уровнем доверия можно принимать каждую информацию. Это инструмент набора `omega-`, построенный по Clean Architecture — подробности см. в `docs/PRODUCT_SCOPE.md` и `docs/DATA_SOURCES.md`.

## 1. Видение и границы

Omega-track отвечает на два вопроса: «кто эта цель?» (идентичность по RDAP/DNS/сертификатам/репутации) и «как до неё добраться?» (сетевой маршрут NeoTrace, GeoIP, ASN). Он дополняет `omega-check` (сетевая открытость), `omega-scan` (гигиена HTTP/HTTPS) и `omega-deep` (ограниченный анализ архитектуры), не дублируя их.

### Что делает Omega-track

- Принимает цель в виде IP, IPv6 или доменного имени, сохранённую и при желании закреплённую (долговременное разрешение).
- Собирает публичные сведения — пассивные или явно включённые профилем (RDAP, DNS, Certificate Transparency, архивы Wayback, анонсы BGP).
- Выполняет расширенный traceroute в стиле NeoTrace (единственное активное сетевое действие в ядре продукта).
- Обогащает каждый значимый IP с помощью локальной базы GeoIP (DB-IP Lite без ключа, MaxMind GeoLite2 по желанию с ключом).
- Опрашивает, с ключом пользователя, источники репутации (VirusTotal, HIBP), всегда раскрывая квоту и отправляемые данные до любой активации.
- Связывает наблюдаемые данные в согласованный профиль с явным уровнем доверия для каждого значения.
- Хранит цели, запуски, результаты, ошибки и экспорты локально (SQLite, `./var/`).
- Предоставляет TUI на Textual и CLI, строго равнозначные по функциям.
- Создаёт отчёты HTML (5 тем, встроенный граф связей Mermaid), JSON, Markdown, CSV, а также самостоятельные файлы DOT и Mermaid.

### Чего Omega-track не делает

| Функция | Ответственный инструмент |
|---|---|
| Сканирование портов, определение служб и баннеров | OMEGA-CHECK |
| Проверки HTTP/HTTPS, заголовки, TLS, веб-гигиена | OMEGA-SCAN |
| Обход, проход по архитектуре и спуск к связанным целям | OMEGA-DEEP |
| Удалённый обход страница за страницей (ссылки, файлы) | OMEGA-FOLD |
| Нагрузочные тесты | OMEGA-STRESS |
| Фаззинг и тесты устойчивости приложений | OMEGA-FUZZ |

Чего следует избегать, в том числе за рамками MVP: перебор поддоменов, сканирование портов, веб-обход, навязчивый сбор персональных данных, автоматизация обхода защит, хрупкий скрейпинг платформ, требующих аутентификации, поиск людей/соцсетей/pastebin-утечек, периодическое/регулярное наблюдение за целью (см. `docs/PRODUCT_SCOPE.md` §7 "Сознательно отложено").

### Предупреждение о разрешённом использовании

Omega-track — инструмент сетевого расследования для законного использования: аудита собственной инфраструктуры, реагирования на инциденты, наблюдения за периметром, который вы вправе документировать. Сбор остаётся почти полностью пассивным/публичным (RDAP, DNS, журналы CT — данные, которые цель или её регистратор уже публикуют), за исключением traceroute (лёгкое активное действие, всегда видимое в используемом профиле).

**Никакое наблюдение не начинается на незакреплённой цели без явного подтверждения** (`--authorize` в CLI, подтверждение в TUI). Только вы отвечаете за проверку того, что ваше использование соответствует применимому законодательству и условиям использования опрашиваемых сторонних источников.

## 2. Установка

### Требования

- Python 3.10+
- Подключение к Интернету — для зависимостей и опрашиваемых пассивных источников
- Установленный `traceroute` или `tracepath` (модуль NeoTrace) — при его отсутствии функция аккуратно отключается, остальная часть инструмента работает как обычно

### Установка

```bash
[ -d omega-track ] && echo "ℹ️ Уже распаковано здесь, шаг пропущен." || tar -xzf omega-track.tar.gz
cd omega-track/
chmod +x install.sh
./install.sh
```

`install.sh`:

1. Создаёт виртуальное окружение `.venv`, если его ещё нет.
2. Устанавливает зависимости (`pip install -e .`, `pyproject.toml` остаётся единственным источником истины).
3. Делает `omega-track.sh` и `install.sh` исполняемыми.
4. Добавляет псевдоним `track` в `~/.bashrc` и `~/.zshrc` (без дубликата, если он уже есть).

### Зависимости

Объявлены в `pyproject.toml` (без отдельного `requirements.txt`):
- `omega-lib`: общая библиотека набора (`ConfidenceLevel`, темы, определение терминала)
- `textual`: интерфейс TUI, темы, автоматическая подстройка под терминал
- `dnspython`: прямое и обратное разрешение DNS
- `httpx`: зонды RDAP/CT/архивов/BGP/VirusTotal/HIBP
- `maxminddb`: чтение локальных баз GeoIP (DB-IP Lite, MaxMind GeoLite2)
- `jinja2`: шаблоны для экспорта HTML
- Зависимости для разработки (`pip install -e ".[dev]"`): `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-httpserver`, `ruff`, `mypy`, `import-linter`

## 3. Использование

### Интерактивный режим (TUI)

Рекомендуется для повседневной работы — запуск без аргументов:

```bash
./omega-track.sh
```
если вы создали псевдоним, просто введите `track` в терминале:
```bash
track
```

Маршрут: заставка (закрывается по нажатию клавиши или щелчку) → главное меню (Цели / Tracker / Результаты / История / Панель / GeoIP / Источники с ключом / Настройки / Справка) → ввод или выбор цели (явное подтверждение, если она не закреплена) и выбор модулей сбора → наблюдение (индикатор и ход операций в реальном времени, с возможностью отмены) → подробные результаты по вкладкам (Идентификация/DNS/Сеть / ASN/NeoTrace/Сертификаты/Архивы/Связи/Диагностика, экспорт) → история/панель/настройки из главного меню. Подстройка под терминал (цвета, размер, структурное упрощение) выполняется автоматически.

#### Сочетания клавиш

| Клавиша | Действие |
|---|---|
| `↑` / `↓` | Перемещение между элементами экрана |
| `Tab` / `Shift+Tab` | Перемещение между полями формы |
| `Esc` | Возврат на предыдущий экран (подтверждение выхода на главном экране) |

| `r` | Обновить определение терминала |
| `a` | Показать справку |
| `q` | Выйти (с подтверждением) |

### Языки интерфейса

Интерфейс доступен на 17 языках: французском, английском, испанском, португальском (Бразилия), итальянском, немецком, нидерландском, польском, русском, упрощённом китайском, вьетнамском, тайском, индонезийском, японском, корейском, хинди и арабском. Выбор делается в Настройках («Langue / Language») и применяется после перезапуска интерфейса; переменная `OMEGA_TRACK_LANG` (например, `OMEGA_TRACK_LANG=ru ./omega-track.sh`) задаёт язык на один сеанс. При запуске из omega-suite omega-track использует язык набора. В текстовой консоли Linux (TTY) языки с нелатинским письмом отображаются на английском на время сеанса. Командная строка остаётся на французском.

### Режим для сценариев (CLI)

Любая подкоманда включает режим CLI:

```bash
# Цели
./omega-track.sh target add example.org --alias "сайт-витрина" --tag prod
./omega-track.sh target list
./omega-track.sh target pin <target_id>

# Запуск наблюдения и отслеживание
./omega-track.sh track run <target_id> --module dns --module rdap --module neotrace --authorize
./omega-track.sh track status <run_id>
./omega-track.sh track show <run_id>
./omega-track.sh track replay <run_id> --authorize

# История
./omega-track.sh history list --target <target_id> --status completed --since 2026-01-01

# Экспорт — 6 форматов, 5 тем для HTML
./omega-track.sh export <run_id> --format html --theme omega-neon --redact contacts_only

# GeoIP
./omega-track.sh geoip status
./omega-track.sh geoip update --provider dbip

# Источники репутации с ключом (раскрытие показывается до любого сохранения)
./omega-track.sh source list
./omega-track.sh source info virustotal
./omega-track.sh source configure virustotal <ключ_api>

# Настройки и очистка
./omega-track.sh config show
./omega-track.sh cleanup preview --older-than 30
./omega-track.sh cleanup run --older-than 30 --yes

# Локальная диагностика (версии, возможности, пути, состояние GeoIP)
./omega-track.sh diagnostics
```

Любая подкоманда принимает `--json` для строго машиночитаемого вывода.

#### Коды выхода

| Код | Значение |
|---:|---|
| `0` | Успех (наблюдение завершено, `COMPLETED`) |
| `1` | Ошибка проверки (недопустимая цель, неизвестный формат экспорта, недопустимый переход состояния, отсутствует ключ API...) |
| `2` | Цель не разрешена (не закреплена и нет `--authorize`) |
| `3` | Ресурс не найден или источник недоступен (неизвестная цель/запуск, сбой загрузки GeoIP) |
| `4` | Частичное наблюдение (`PARTIAL`) — не сбой, успешно выполнились лишь некоторые модули |
| `5` | Непредвиденная внутренняя ошибка |
| `130` | Прервано пользователем (`Ctrl+C`) |

### Допустимые форматы цели

```text
192.168.1.10                IPv4
2001:db8::1                 IPv6
example.org                 Домен
```

Подробности по каждому источнику, квоты и лицензии: `docs/DATA_SOURCES.md`.

## 5. Архитектура

Omega-track построен по **Clean Architecture** (domain / application / infrastructure / interfaces / ports / core / app / plugins), следует шаблону набора `omega-` (см. `omega-check`/`omega-fold`) и проверяется `import-linter` при каждом изменении.

```text
src/omega_track/
├── domain/          Чистая бизнес-логика (цели, TrackRun/ModuleRun, findings, связи, профили...)
├── application/     Сценарии использования (commands/queries/оркестраторы фаз/политики)
├── ports/           Контракты, ожидаемые приложением (сборщики, репозитории, экспортёры...)
├── infrastructure/  Конкретные реализации (dnspython/httpx/subprocess/maxminddb, SQLite, jinja2)
├── interfaces/      tui/ (Textual) и cli/ (для сценариев), строго равные по функциям
├── app/             Сборка (DependencyContainer, bootstrap, жизненный цикл)
├── core/            Общий словарь (версии, реэкспорт из omega-lib)
└── plugins/         Необязательные модули с одним источником (CT, архивы, BGP, VirusTotal, HIBP)
```

Правила проектирования:
- `domain/` никогда не работает с сетью и I/O; `infrastructure/` работает с сетью и I/O, но никогда не выносит суждений.
- `interfaces/` отображает и не содержит бизнес-логики — CLI и TUI вызывают строго одни и те же сценарии.
- 1 модуль сбора = 1 источник = 1 статус (`ModuleRun`): никогда два источника не объединяются под одним неоднозначным статусом.
- Отсутствие отдельного поля никогда не считается ошибкой; только полная недоступность источника приводит к `SKIPPED`/`FAILED`.

## 6. Источники данных

| Источник | Поставщик | Ключ | Режим |
|---|---|:---:|---|
| Прямой/обратный DNS | Системный резолвер | нет | Лёгкий активный |
| RDAP | Bootstrap IANA → RIR/регистратор | нет | Публичный пассивный |
| Certificate Transparency | `crt.sh` (Sectigo) | нет | Публичный пассивный |
| Веб-архивы | Wayback Machine (Internet Archive) | нет | Публичный пассивный |
| BGP / сетевые анонсы | RIPEstat (RIPE NCC) | нет | Публичный пассивный |
| GeoIP | DB-IP Lite (по умолчанию) или MaxMind GeoLite2 | нет / да | Офлайн (локальная база) |
| NeoTrace | Локальный `traceroute`/`tracepath` | нет | Лёгкий активный |
| Репутация | VirusTotal | да (бесплатный) | С ключом |
| Репутация | Have I Been Pwned | да (платный) | С ключом |

Точные квоты, лицензии и запасные варианты для каждого источника: `docs/DATA_SOURCES.md`. Ни один ключ API никогда не появляется в журналах, экспортах или на экранах диагностики.

## 7. Политика доверия

Каждое собранное поле получает один из уровней (общих для всего набора через `omega-lib`):

| Уровень | Значение |
|---|---|
| `VERIFIED` | Протокольный факт, наблюдаемый напрямую, который цель не может подделать (напр.: прямой ответ DNS, локальное измерение traceroute). |
| `DECLARED` | Значение, заявленное самим источником в поле, которое он полностью контролирует (напр.: данные RDAP, показанные регистратором) — правдоподобно, но подделывается по желанию. |
| `CORROBORATED` | Значение `DECLARED`, подтверждённое независимым признаком (напр.: домен, замеченный как минимум в двух разных журналах Certificate Transparency). |
| `INFERRED` | Выведено из шаблона/эвристики без явного заявления (напр.: общий ASN, указывающий на связь; никогда не повышается автоматически). |
| `UNKNOWN` | Нет пригодного признака, либо цель его активно скрывает. |

Общая оценка доверия к наблюдению — подспорье при чтении, а не вердикт безопасности.

## 8. Уровни сбора, разрешение и редактирование

Каждый профиль явно указывает характер своих действий (`CollectionMode`):

- **Офлайн**: проверка цели, чтение локальной GeoIP, корреляции по уже сохранённым данным, экспорты — без сети.
- **Публичный пассивный**: RDAP, публичный DNS, журналы CT, архивы, BGP — третьей стороне передаётся только запрашиваемая цель, это свойство самого протокола.
- **Лёгкий активный**: разрешение DNS, обратный DNS, traceroute — запрос видят резолвер, настроенный на машине, и каждый промежуточный маршрутизатор на пути.
- **С ключом пользователя**: поставщики, требующие ключа или вводящие квоты, включаются только после явной настройки и показанного раскрытия (квота, отправляемые данные).

**Защита разрешения**: никакое наблюдение не начинается на незакреплённой цели без явного подтверждения (`--authorize` в CLI, флажок в TUI). Закрепление цели разрешает её на постоянной основе для будущих наблюдений.

**Редактирование экспортов**: каждый экспорт принимает политику (`none`/`contacts_only`/`sensitive_only`/`strict`), которая скрывает чувствительные поля (в частности, контакты RDAP) в экспортируемом результате — локальное хранилище при этом всегда сохраняет полные собранные данные. Подробности: `docs/PRIVACY.md`.

## 9. Совместимость с терминалами

TUI (Textual) автоматически определяет возможности терминала (эмулятор, размер) и соответственно подстраивает свою структурную таблицу стилей (`complete`/`standard`/`reduced`/`mono`), без ручного флага. Режим CLI всегда остаётся простым текстом, не зависящим от терминала. Политика общая для всего набора `omega-` (`omega-lib`, `terminal/policies.py`).

### Профиль по обнаруженному эмулятору

| Эмулятор | Начальный профиль |
|---|---|
| Ghostty, Alacritty, WezTerm, Kitty | `complete` |
| Konsole, GNOME Terminal, Terminator, Xfce4 Terminal | `standard` |
| xterm, urxvt, современный SSH | `reduced` |
| TTY Linux, старый SSH | `mono` |
| Нераспознанный эмулятор | `reduced` (запасной вариант по умолчанию) |

### Профиль по размеру терминала

| Минимальный размер (столбцы × строки) | Предел профиля |
|---|---|
| 120 × 32 | `complete` |
| 100 × 28 | `standard` |
| 80 × 24 | `reduced` |
| меньше | `mono` |

Итоговый профиль — **более строгий из двух** (эмулятор и размер). Его можно обновить в реальном времени клавишей `r`.

## 10. Экспорты

Отчёты Markdown и HTML пишутся на языке, выбранном в Настройках («Язык экспорта», по умолчанию — язык интерфейса); JSON, CSV, DOT и Mermaid остаются данными и не переводятся. Отчёты по умолчанию создаются в `var/exports/` (путь выполнения, привязанный к папке проекта, `$OMEGA_TRACK_VAR_DIR` — чтобы его переопределить) или по указанному пути (`--output` в CLI, диалоговое окно в TUI). Уникальное имя файла с отметкой времени: `{отметка_времени}_{цель}_{короткий_id}.{расширение}`.

| Формат | Содержимое |
|---|---|
| `json` | Полная структура наблюдения (`TrackRun` + findings + связи), источник истины, строго сериализуется в JSON |
| `markdown` | Компактный отчёт для человека, читаемый вне терминала |
| `html` | Самостоятельный веб-отчёт, 5 тем на выбор (`--theme`), граф связей Mermaid встроен inline |
| `csv` | По одной таблице на категорию findings |
| `dot` | Граф связей Graphviz, самостоятельный файл |
| `mermaid` | Граф связей Mermaid, самостоятельный файл |

## 11. История, очистка и повтор

Каждое наблюдение сохраняется (SQLite, `var/db/omega-track.db`): история с просмотром и фильтрами (цель/статус/тег/период), сводная панель (распределение по статусам, надёжность модулей, типология последних findings), повтор наблюдения на той же цели без повторного ввода (`track replay`) и очистка старой истории с обязательным предпросмотром перед любым удалением (`cleanup preview` перед `cleanup run --yes`).

## 13. За рамками

- Полная история WHOIS/DNS, коммерческий passive DNS
- Поиск людей, соцсетей, pastebin/утечек
- Сканирование портов, определение служб и баннеров (`omega-check`)
- Проверки HTTP/HTTPS, заголовки, TLS (`omega-scan`)
- Обход и проход по архитектуре (`omega-deep`/`omega-fold`)
- Нагрузочные тесты (`omega-stress`), фаззинг (`omega-fuzz`)
- Интерактивная карта в TUI (предназначена только для экспортированного отчёта HTML)
- Непрерывный MTR, с несколькими зондами и точками наблюдения
- Пакетный/периодический режим или регулярное наблюдение за целью — `TrackRun` всегда остаётся явным ручным действием
- Движок миграции схемы SQLite (аддитивная схема, та же практика, что и в остальном наборе)
